Overview

This résumé site is intentionally a small, working demonstration of the platform-engineering practices described in the résumé itself: a golden-path static-site deployment on AWS, all infrastructure defined as code, a real CI/CD pipeline with no long-lived secrets, and documented AI-assisted build process. The site is not a novelty — the architecture is the point.

Why this matters for the DevEx role: The job description asks for hands-on experience with internal developer platforms, golden paths, IaC, GitHub Actions, and evaluating AI-assisted engineering practices. This project exercises all of those muscles on a real, public artifact.

Architecture

Hosting: S3 + CloudFront (Origin Access Control)

Site files live in a private S3 bucket — no public access is enabled at the bucket level. A CloudFront distribution sits in front using Origin Access Control (OAC), the current AWS-recommended approach (replacing the legacy Origin Access Identity). CloudFront is the only authorized principal that can read objects from the bucket.

This is the textbook "golden path" architecture for static sites on AWS: fast global edge delivery, HTTPS enforced end-to-end, origin kept private, and essentially zero operational overhead at this traffic level.

Caching Strategy

  • HTML files — Cache-Control: no-cache (1-second CloudFront TTL). Updates appear immediately after a CloudFront invalidation.
  • Static assets (CSS, JS, images) — long cache TTL (1 year). These are treated as immutable; change the filename/hash to bust cache.

HTTPS & Custom Domain

HTTP-to-HTTPS redirect is enforced at the CloudFront level. The site currently runs on a *.cloudfront.net domain. The CDK stack is structured so a custom domain + ACM certificate can be added later by uncommenting a small block in the stack file — no rebuild required. See infra/README.md for the exact steps.

Infrastructure as Code: AWS CDK (TypeScript)

All AWS resources — the S3 bucket, CloudFront distribution, OAC, bucket policy, and cache behaviors — are defined in a single CDK stack (infra/lib/resume-site-stack.ts). No resources were created manually in the console. This means:

  • The infrastructure is reproducible, reviewable, and version-controlled.
  • Drift is detectable via cdk diff.
  • Teardown is a single cdk destroy.

CI/CD Pipeline (GitHub Actions)

No Long-Lived AWS Keys

The pipeline uses GitHub OIDC federation to assume an AWS IAM role — there are no AWS access keys stored as GitHub secrets. On each push to main, GitHub presents a short-lived OIDC token; AWS STS validates it and issues temporary credentials scoped to exactly the permissions needed for deployment.

This is a meaningful DevSecOps detail: credential rotation is automatic, blast radius is limited, and there are no static secrets to leak or rotate.

Deploy Workflow (deploy.yml)

  1. Check out code.
  2. Install Node dependencies for the CDK app (infra/).
  3. Assume the deployment IAM role via OIDC (aws-actions/configure-aws-credentials).
  4. Run cdk deploy --require-approval never to provision/update infrastructure.
  5. Sync site files to S3 (aws s3 sync) with appropriate cache-control headers.
  6. Create a CloudFront invalidation for /* so updated HTML is served immediately.

PR Infrastructure Diff (cdk-diff.yml)

On pull requests that touch infra/**, a separate workflow runs cdk diff and posts the output as a PR comment. Infrastructure changes are visible in review before merge — a small but meaningful guardrail that mirrors enterprise change-management practices.

Content Architecture: Data-Driven Résumé

Résumé content lives in site/content.json — a structured JSON file separate from the HTML template and rendering logic. Updating the résumé means editing the JSON, not touching HTML. The renderer (site/build.js) reads the JSON at page load and populates the DOM.

This "content as data" separation mirrors the golden-path / platform-template pattern central to developer experience work: the what (content) is decoupled from the how (template), so authors don't need to understand the rendering layer to update content.

DevSecOps CI Hardening

The pipeline described above also carries three concrete DevSecOps controls, all enforced automatically on every push/PR rather than relying on a manual review step:

  • CodeQL static analysis (SAST) — scans infra/** TypeScript and site/** JavaScript on every push to main, every PR, and a weekly schedule.
  • Dependabot — weekly automated PRs for outdated npm packages (infra/, with AWS SDK/CDK packages grouped to reduce noise) and GitHub Actions versions.
  • Gated npm audit — a required CI step in both cdk-diff.yml and deploy.yml that fails the build on newly introduced vulnerabilities above a configured severity threshold.

These badges are GitHub's own live status images — they aren't screenshots, they update automatically as the workflows run. See the Security Scorecard for a working artifact built the same way as the DORA metrics page: a scheduled job pulls this repo's own CodeQL alert counts, Dependabot PR activity, and current npm audit findings and renders them live.

AI-Assisted Build Process

What Was AI-Assisted

  • Initial scaffolding — project structure, CDK stack skeleton, GitHub Actions workflow YAML, and this prose were drafted with Claude (Anthropic) as a co-author, guided by specific prompts describing the architecture requirements.
  • CSS design system — the custom-property-based stylesheet was drafted by the AI and reviewed/adjusted for accessibility (contrast ratios, focus styles, responsive breakpoints).
  • IAM policy scoping — the AI drafted least-privilege IAM policy statements; each was reviewed against AWS documentation before use.

What Was Human-Reviewed and Edited

  • All résumé content — sourced directly from the source résumé document. No AI-generated claims about experience, titles, dates, or metrics.
  • Security choices — OIDC over static keys, OAC over public bucket, block-public-access settings — each was a deliberate decision, not an AI default.
  • CDK construct selection — e.g., choosing aws_cloudfront.Distribution with OAC over the legacy CloudFrontWebDistribution.
  • This write-up — drafted with AI assistance, then read and edited by hand for accuracy and tone.

The Broader Point

AI assistance accelerated the initial scaffolding significantly — the kind of work that normally takes an hour of copy-pasting boilerplate took minutes. The value was in moving quickly from "blank repo" to "working skeleton" so human judgment could be applied to the parts that matter: content accuracy, security posture, and architectural decisions. That is exactly the model the DevEx role is meant to enable at scale.

Estimated AWS Cost

At resume-traffic volumes (tens to low hundreds of requests/month):

  • S3: effectively $0.00 (well under 1 GB storage, negligible GET requests via CloudFront).
  • CloudFront: 1 TB free transfer/month on the free tier; well under that. Estimated < $0.50/month after free tier.
  • Data transfer: negligible at this traffic level.
  • Total estimated monthly cost: < $1.00, likely $0.00–$0.10 in practice.

Adding a Custom Domain (Future)

To add a custom domain (e.g., resume.example.com):

  1. Request a public ACM certificate in us-east-1 (required for CloudFront).
  2. Uncomment the domainNames and certificate props in infra/lib/resume-site-stack.ts.
  3. Add an ARecord in Route 53 pointing to the CloudFront distribution.
  4. Run cdk deploy.

The stack is already structured for this — no redesign needed.
